# NAS 自主管理照片层级与全量缩略图重建

日期：2026-09-29。状态：准备方案，尚未实施或执行生产清理。

## 已确定的需求

- 小预览满足 iPhone 网格不展开时清楚，终端允许保存全库小预览。
- 标准照片保留现有 JPEG / HEIF，不为统一格式转码；NAS 长期保存，终端按需缓存。
- RAW 有则保留，没有不要求。所有原始文件保持不变。
- 重建、进度持久化、重试和重启恢复全部由 NAS Docker 服务承担，不依赖 Mac 在线。
- 新照片入库与历史缓存重建使用同一条数据库驱动的处理流程；外部只监控进度和错误。
- 照片、视频、目录使用三个独立实体表，文件关联记录表达标准照片、RAW 和实际目录位置；迁移保留资产身份、版本和整理数据。
- 首次重建低负载运行，每轮领取数量、并发数量和编码资源均设上限，不追求尽快跑完全库。
- 原片、RAW、sidecar 和长期保存的标准照片不属于可删除缓存；生成的标准照片应放在 KEEPS_ROOT 之外的专用照片位置。

## 当前实现证据

- `server/src/media.rs::generate_preview` 生成最长边 1200px、quality 80 的 HEIC。
- `server/src/worker.rs::ensure_default_preview` 对已存在对象直接返回，没有生成规格的版本判断。
- `server/src/jobs.rs` 已有持久化扫描队列、文件状态与重启恢复；现有任务以 folder 为单位，不能假定已经支持全库逐资产重建。
- `server/src/versions.rs` 已有默认文件版本和路径证据。不能用文件名猜测 JPEG 与 RAW 属于同一照片。
- `shared/Sources/KeepsAPI/Models.swift` 仅提供一个 preview；网格与查看器需拆分媒体用途。
- `shared/Sources/KeepsAPI/PreviewCache.swift` 使用服务器、资料库、资产和内容版本作为身份，统一 5 GiB 淘汰策略；尚不支持角色分离或全库下载。
- `shared/Sources/KeepsAPI/KeepsPhotoGrid.swift` 的 iPhone 大、中、密集视图分别以 3、5、9 列为基准，等面积布局使个别照片宽度不同。
- 本次讨论前的 NAS 数据库落盘快照记录约 12.4 万张预览、73 GB 文件字节；它不是本方案执行时的实时基线。

## 重建方式

建议逐资产重建、切换后清理。每张照片仍从源文件完整重新生成，不复用旧预览作为编码输入。

另外两种方式的取舍：先全部删除会让整个图库在重建期间缺图，且源文件不可用时无法恢复；全部生成后统一切换需要同时容纳两套缓存。逐资产替换可保留可用性并及时释放已淘汰缓存。

1. NAS 生成基线清单，记录资产、选定源版本、已有对象、可读性、规格、字节数和可用空间。通过服务支持的方式备份数据库与任务状态，不通过 SMB 修改在线 SQLite。
2. 在 NAS 上选取分层样本（本次 28 张尺寸样本及另 16 张质量样本），包含 JPEG、HEIF、RAW-only、横竖图、全景、暗光噪点及复杂纹理。比较最长边 384/512/640px 的 HEIF 缩略图，测量平均值、P95、最大值与编码耗时。
3. 以 iPhone 最大常用网格及屏幕倍率验收清晰度；不把 384px 或 15–30 KB 当作已验证规格。抽样阶段确定单一小预览规格和编码质量，保留方向与正确色彩，去除不必要元数据。不新增中间预览层。
4. 为全库资产创建持久化重建工作项，记录源内容版本与生成规格版本。复用现有任务系统扩展，不另起 Mac 脚本或第二套调度服务。按资产去重，包含隐藏和回收站资产的既有缓存；源不可用的资产单独列为失败，不伪报完成。
5. 先使用一个 NAS 编码 worker，抽样确认负载后再决定是否提高并发。每项执行：校验源 → 临时输出 → 解码/尺寸/哈希检查 → 原子发布文件 → 核对源版本仍有效并事务更新引用与目录修订号 → 标记完成。
6. 默认版本或源内容在执行中改变时，丢弃该次未发布结果并重新排队；不得把旧源缩略图登记到新版本。容器重启后从持久状态恢复，已完成相同源与规格的项目直接跳过。
7. 清理只处理专用缓存目录中已无当前引用的生成对象，避开正在写入的对象，并等待旧签名 URL 的 15 分钟有效期及传输宽限期结束。失败项保留可用旧预览，修复后继续。临时工作目录随任务退出清理；当前 GC 只覆盖已登记的替换对象，未登记孤立对象不自动删除。
8. 完成后核对每个可用资产的新规格覆盖率、实际文件可读性、数量和总大小，列出所有失败项。失败数非零时报告部分完成，不宣称全库重建完成。

## 数据库驱动与处理上限

照片、视频先入库，再由 NAS 服务内部定时任务处理。缓存记录保存待生成／生成中／就绪／失败状态、源版本、规格版本、对象路径和大小、最近错误、尝试次数与下次重试时间。就绪状态只能在文件成功发布后写入；定期分批核对文件存在性，丢失时重新进入待生成。目录表只管理目录关系，不把目录当作媒体缓存任务。

以这些持久状态扩展现有 jobs 存储和 worker，不引入独立消息队列或外部 crontab。历史重建、正常新增、源变化、规格升级和缓存缺失都通过同一状态转换处理。视频封面同样受限；视频转码不在本次范围内。

首次运行采用以下保守初始值。当前实现固定批量 20、并发 1、休息 60 秒；编码质量与 Docker 资源限额可配置，其余调参需修改代码并重建：

| 控制项 | 初始值／行为 |
| --- | --- |
| 单轮领取上限 | 20 个媒体资产；失败尝试也计入，样本比较分轮执行 |
| 媒体处理并发 | 全服务最多 1 个，包括新增、重建、RAW 标准照片生成和视频封面生成 |
| 编码线程 | 编码器配置线程 1，容器绑定单核；底层库仍可能创建辅助线程 |
| 轮间休息 | 上轮结束后休息 60 秒，再领取下一批；轮次不重叠 |
| 调度领取 | 数据库事务领取，不在内存中加载全库待处理项 |
| 重试 | 失败后递增延迟，连续失败达到有限次数后保留失败状态，等待修复并显式重试 |
| 磁盘不足 | 停止领取新任务，保留进度和错误；满足空间条件后继续 |

批量数量限制不能替代 CPU／内存限制：一张大型 RAW 也可能消耗较多资源。实施时对读取、解码、编码子进程设置时间和资源边界，核对现有 ImageMagick 限制是否覆盖 RAW 解码器及 HEIF 编码器；根据 NAS 可用资源实测配置 Docker 的 CPU／内存上限，并为 HTTP 与数据库留出余量。完整尺寸标准照片编码上限为 900 秒；小图/旧预览仍为 180 秒。超时或内存限制触发属于可报告的失败，不能把未完整生成的文件标为就绪。不在未知 NAS 容量时写死容器内存值。

新增与重建共享同一个全局并发上限，不能各自启动一个 worker 绕过限制。定时触发发现已有轮次运行时不启动第二轮。单轮内部逐项持久化，容器重启只恢复中断项，完成项不重复生成。不自动提升并发；首次实测稳定后再决定是否修改限额。

外部只读监控至少提供：待生成／处理中／就绪／失败数量、当前批次处理量、最近成功时间、单位时间吞吐、最近错误及磁盘余量。NAS 负载与容器内存通过运行环境监控读取，进度和错误由服务 API 提供。预计耗时使用 NAS 实测速率，不根据 20 张／轮假定固定吞吐。

本次提供有上限的显式重建接口：每次将最多 20 个就绪项置回待生成；规格升级自动使全库旧规格入队。生产迁移逐张替换，不实现一次性清空全库；照片／视频／目录表保持完整。

## 标准照片与 RAW

- 同一已确认资产存在可用 JPEG/HEIF 时，直接引用已有标准照片，不复制或重编码，保留用户明确的版本选择。
- RAW-only 需要生成标准照片；该文件是长期保存的照片产物，不纳入此次缓存删除。创建前需确定 KEEPS_ROOT 外的专用输出目录，并只给该目录新增写权限，现有原片挂载保持只读。该部署路径是实施前必须落实的配置。
- 现有未归并的 JPEG/RAW 不在本次重建中自动合并，避免改变照片身份和整理结果。
- 标准照片下载需要增加受鉴权或签名保护的媒体接口，返回准确 MIME、尺寸和内容版本；大文件采用流式传输，不沿用把整个文件读进内存的预览读取方式。路径由服务端现有资产映射解析。
- 小预览由标准照片生成；RAW-only 先生成标准照片再生成小预览。PNG/TIFF 等其他已支持格式需在基线中单独统计，保留源并明确标准照片输出，不能因不属于 JPEG/HEIF 静默漏掉资产。

## 客户端与清理边界

- API 区分小预览与标准照片，缓存身份增加用途和规格版本。网格只下载小预览；查看器先显示已有小预览，再加载标准照片。RAW 不参与普通网格下载。
- NAS 负责生成所有共享图片，终端只负责下载、解码和管理自身缓存；NAS 不能直接删除离线终端的文件。
- 客户端升级时一次性清理旧专用 KeepsPreviews 缓存并进入新缓存空间，同时更新列表描述符；不清除连接凭据或用户设置。离线设备在升级并下次连接后完成迁移。
- 小预览与标准照片分开计量和回收，标准照片下载不能挤掉全量小预览。系统 Caches 仍可能被系统回收，不能承诺绝对永久离线可用。
- 全量小预览下载不是当前客户端已有功能；需实现可恢复的分页预取、版本同步与空间检查，用户正在看的图片优先。iOS 后台执行受系统约束，不承诺退出应用后立即下完整库；NAS 重建不受此影响。
- 服务端先增加新接口和生成能力，客户端更新后再清理旧对象。旧客户端不具备新缓存契约，不能仅部署 NAS 就宣称整个系统完成迁移。

## 实施顺序与验收

1. NAS 样本实测，确定规格、空间预算及预计耗时；确认 RAW-only 标准照片的存放配置。
2. 扩展现有媒体模型、标准照片读取 API 和 NAS 持久重建任务；保留现有业务数据。
3. 更新共享客户端、iPhone 网格与照片查看器、Mac 对应入口及缓存迁移。
4. 在隔离测试库验证：原片哈希不变、任务重启续跑、失败重试、源版本并发变化、引用切换与清理顺序、签名下载、用途隔离和磁盘不足处理；验证每轮不超过 20 项、新增与重建合计并发不超过 1、轮次不重叠、编码资源限制有效。
5. 部署到 NAS 与测试客户端，确认 iPhone 网格清晰度及 JPEG/HEIF 大图首次打开速度，再启动 NAS 全库重建。
6. 记录 fresh NAS 任务结果、数据库引用与实际文件核对，以及终端旧缓存迁移结果。实际部署及验证状态以 docs/validation/2026-09-29-thumbnail-pipeline-nas.md 为准。

不删除数据库、ledger、评分、标签、追踪配置、文件版本、原片、标准照片或 RAW；不重建整个业务索引来代替图片缓存重建。
